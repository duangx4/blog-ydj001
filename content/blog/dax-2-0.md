八月写过一篇[《我的 DAX》](/blog/dax-personal-agent/)，讲这套系统是什么、为什么自己搭。一个多月过去，它在十月初经历了一次整体换代：框架、入口、模型通道全换了，运行到现在一周多。

这篇不重复上一期的定位介绍，只写换代本身：**换了什么、为什么换、现在跑成什么样、还有哪里没修好。**

## 先说结论

1.0 是把一个 agent 装进某个现成的框架，能力长在框架的插件体系里；2.0 是把「系统」和「框架」拆开——能力写成自己目录下的文件，框架只是执行器，坏了可以换。

换完之后，真正质变的部分不是功能变多，而是**它开始自己巡检自己**：七个定时任务里有一半是给自己做体检和预检的，出问题先自己修，修不了才来叫人。

## 为什么非要换

驱动这次大修的是三个具体的问题，不是什么架构洁癖。

**第一，资产被框架绑死。** 1.0 的记忆、技能、插件都是那个框架的私有格式，升级是件高风险的事——不升，就带着已知问题一直跑；升，几个月攒下来的资产可能被洗掉一层。十月真的经历了一次：换框架之后，几十个技能和知识库没能自动跟过来，只能从当时的只读归档里一份份捞回来。这种「换个底座就掉一层皮」的结构，越早拆越好。

**第二，入口绑在了一个我控制不了的通道上。** 1.0 的主要对话入口是 QQ 机器人。机器人掉线、平台改协议，整套系统就哑了——而这恰好是十月正在发生的事（后面「还没修好的」一节会讲）。

**第三，模型散在各处，账看不见。** 三个中转站、十几条模型，哪个还能用、这个月花了多少，全靠人记。工具多到一定程度，管理成本比工具本身还贵。

## 2.0 的四个改动

### 一、能力和框架分开

新框架用的是 Hermes Agent，跑在容器里。关键不在换了哪个框架，而在**目录结构变了**：

- 「怎么做事」的知识全部写成技能文件（当前 100 个），一个技能一个目录，包含步骤、命令、已知的坑。要改，改文件；要带走到别的框架，拷贝目录。
- 长期记忆是两份纯文本（合计一万一千字）：一份记「老大是谁、环境长什么样、约定是什么」，一份记系统本身的坑和口径。
- 运维脚本独立放在自己的脚本目录里，框架的定时任务只是调用器。

这样拆开之后，框架升级只影响执行器，能力资产留在原地。

### 二、入口搬到飞书

所有主动消息——每日简报、体检报告、告警、变更预检——统一投飞书私聊。选择理由很实际：我日常就在飞书上，而且这个入口的自建应用权限、消息接口都在自己手里，不像 QQ 机器人那样受制于第三方协议变更。QQ 保留为备用入口。

### 三、模型收口到一个自建网关

自建了一层 LiteLLM 网关，把三个上游中转站的模型统一收口成一份模型清单（当前 11 个条目，指向 10 个上游模型），路由规则固定成三条：

1. 日常活走便宜的模型；
2. 复杂活升级到大模型；
3. 主通道限流或报错，自动切备用通道，系统不会因为某一家挂了而打不开。

网关顺带把账也管了：按天统计请求数和花费，能看到「哪一天、哪个模型、花了多少」。以前这笔账是黑盒。

顺手做过一次测速：同一个问句走网关、按 15 秒铺开取中位（单次读数不作数），新主通道净解码 167 tok/s（4 样本，区间 110–225），旧上游组同口径 184 tok/s（4 样本，区间 116–192）。两组今天差不多快，说明这次换代拿到的不是峰值速度，而是「模型名一个没改、降级链可控、出问题能一键回滚」。上游组自己抖得很厉害——我这边测速探针的记录里，同一分钟出现过 50 和 245 两个读数。

### 四、自主层：七个定时任务

这是最像「2.0」的部分。全部任务跑在自己的 cron 里，输出投飞书：

| 任务 | 频率 | 干什么 |
|---|---|---|
| 出图队列 | 每 5 分钟 | 扫描需求单，调生图通道，成品落到产出目录 |
| 快巡自愈 | 每 15 分钟 | 探工作台一致性、内网穿透、模型通道；异常自己动手修，一切正常就静默 |
| 博客 PR 哨兵 | 每 15 分钟 | 盯外部投稿的 PR，格式审查通过就自动合并上线 |
| 人生简报 | 每天 08:30 | 汇总待办、日程、笔记 |
| 每日体检 | 每天 09:00 | 九个板块端到端实测，出一份报告 |
| 变更预检 | 每天 10:30 | 检查镜像和依赖有没有新版本，在影子环境里先验，不动线上 |
| 情报侦察 | 每周一 10:00 | 收集值得关注的情报，汇总成简报 |

另有一个**判断门**：执行工具调用之前，先把「打算做什么」交给一个类型化判断模型打分（破坏性、数据外泄风险、影响面），按分数决定放行还是拦截。门现在跑在影子模式——只记录判断结果，不真拦，等数据攒够再决定要不要开成强制。

## 运行一周多的实测数据

以下都是 10-03 到 10-11 之间的实测值，不是设计目标：

| 指标 | 实测 |
|---|---|
| 主容器连续运行 | 8 天，重启 0 次（10-03 起） |
| 定时任务执行 | 最近 1000 条记录全部 completed、0 异常（10-08 起，约 67 小时；记录表只留最近 1000 条） |
| 快巡扫描 | 每 15 分钟一次，最近 50 条记录全部静默（没有需要报的事） |
| 每日体检 | 每天一份报告，10-04 起不间断，逐项实测 |
| 内网穿透 | 13 条隧道全部在线（12 条主实例 + 1 条出图专线独立实例） |
| 模型通道 | 11 个条目 / 10 个上游模型，逐条端到端实测（含 1 条类型化判断通道） |
| 技能 / 长期记忆 | 100 个技能，一万一千字记忆 |
| 日请求量 | 10-08 的 279 次 → 10-10 的 583 次（网关按天统计） |

「全部 completed、0 异常」这种话在运维里最容易骗人，所以补一句判据：体检的每一项都要求**请求真的到达、数据真的一致**，不看退出码、不看服务状态。比如判断内网隧道是否真通，采用的方式是对比本机工作台和公网门户返回的元数据哈希，一致才算通——服务是 active、端口在监听，都不算证据。

## 一条教训：退出码 0 什么都证明不了

这一周多最有价值的收获是一条负面经验。

计划任务的 `LastTaskResult=0`、`systemctl is-active` 输出 `active`、进程还在进程表里——这三样都只能说明「启动器没报错」，不能说明「东西真的通了」。它们给的绿灯是假的，而且假得很安静。

两个真实的例子：

- **手环数据支路。** 体检判断数据新不新鲜，看的是文件里的「更新时间」；而这个时间是解析脚本每跑一次写进去的——脚本每隔几分钟就重跑一次，这个字段就永远显示「刚刚更新」。体检一路绿灯，实际上手机上传的原始数据包停在 9 月 5 日。字段新鲜 ≠ 数据新鲜。
- **QQ 机器人。** 体检只测它的 WebUI 端口，端口永远返回 200，于是体检长期报「正常」。而机器人实际上已经在报身份验证失败，一条消息都发不出去。

现在整套检查口径改成：**只认端到端**。服务状态、退出码、监听端口一律不作为通过依据，必须有一次真实的请求走完整条链路，并且返回内容正确。

## 还没修好的地方

写「运行一周多」如果只列绿灯，那就是宣传稿。下面是目前明确不合格的项：

- **QQ 机器人离线近一个月。** 九月初开始持续报身份验证失败，需要本人重新扫码登录，一直没排上；它现在只是备用入口。
- **手环健康数据支路已挂起。** 我本来就不戴手环，这条链路没有使用价值，暂时不修。
- **判断门还在影子模式。** 只记录、不拦截，等于多了一层观测，少了一层保护。
- **公网门户只有只读展示，没有账号体系。** 写路由全部封锁（空 payload 和合法 payload 都实测返回 403），但登录认证还没做。
- **香港 VPS 被服务商整机冻结过一次。** 症状是所有端口超时、经 Cloudflare 访问返回 522，恢复后系统时钟还落后了。这是租用 VPS 的固有风险，只能靠探测及时发现，没法从根上解决。

## 小结

2.0 最实在的变化不是多了几个功能，是**分层**：能力写成文件，跟框架解耦；入口换成自己能控制的通道；模型和钱都收进一个有账可查的网关；监控交给系统自己，而不是等我发现。

1.0 时代我最担心的是「框架不升级会烂，升级会丢」；2.0 之后这个问题变成了「换执行器要花半天」——这才是我想住的结构。
