2025 年 12 月 20 日，校内工程挑战赛，践行楼 204。六个人的队，一辆初始尺寸不到 30 厘米的小车。我的活是让它动起来、按线跑、把弹丸扫进筐里。

最后进了八强——没有奖状，只有赛后群里的记录。三轮比赛，第三轮上场不到一分钟就离场了，原因不是代码，是我们换备用电机时装反了。

这篇写清楚三件事：固件怎么从第一版长到参赛版，哪些参数是拿命试出来的，以及哪里其实没做好。

## 先说结论

| 项 | 数 |
|---|---|
| 备战跨度 | 2025-12-01 16:17 → 2025-12-20 15:48，19 天 |
| 固件目录 | **17 个**（其中 2 个是重复版本与备份点，**真正不同的代码 15 份**） |
| 最长一版 | `car2.5 增加运动速度挡位`，1001 行 |
| 参赛版 | `car2.4 - 双电机+舵机`，866 行 |
| 架构 | STM32F103C8T6 + HAL 库 + Keil MDK + CubeMX |
| 执行机构 | 四轮差速底盘、双 TT 减速电机扫弹、舵机、四路灰度、USART1 蓝牙 |
| 结果 | 八强，无奖状佐证 |

三条教训，按对我的用处排序：

1. **不是代码推倒，是车推倒。** 麦轮方案跑了 5 版，最后不是代码不行，是没时间把麦轮调出来，换了硬件——于是代码只能从空工程重建。
2. **巡线的修正量不能调小。** 微调速度从 50 提到 190 才跑得住，低速修正反而会出线回不来。
3. **赛前没装的那行互锁，和赛前装反的那台电机，是同一类错误**：都指望人不出错，而不是让系统不给出错的机会。

## 一、这是个什么比赛

比赛分两段，时间卡得很死。这两段的时间账决定了后面所有技术取舍。

| 项目 | 内容 |
|---|---|
| 赛制 | 淘汰赛，抽签分组，5–6 人一队 |
| 自动阶段 | **45 秒**，可选自动巡线，要过直角弯停进预备区 |
| 手动阶段 | **4 分钟**，手动操控收弹丸 |
| 出弯硬线 | 手动阶段 **1 分钟内必须出弯**，否则拿 80% 负增益 |
| 计分 | 小弹丸 1 分、大弹丸 10 分；倒入容器内的 **×2**，掉出车筐不计 |
| 复位代价 | 小车异常复位到启动区，**扣 2 分** |
| 尺寸 | 初始 ≤300³ mm，变形后 ≤400³ mm，轮径 ≤100 mm |

规则里有两条绑死电控：

- **底盘电机指定 TT 电机或 TT 金属电机**，减速比只能 1:48 或 1:90，检录要出示商品参数截图。这条直接决定了速度上限——不是你想多快就多快。
- **自动巡线期间扫弹机构不得启动**。这条后来成了全文最尴尬的一段，第七节会回扣。

难度还不止时间。规则里电控这一组**没有独立的增益项**——结构和电路组的每一个动作都能换来百分比加分（图纸相似度、自研最小系统、PCB 画/焊/上车各档叠加），而电控只有"让车按规则动起来"这一个及格线。车动不了，前面所有加分都是零。

## 二、为什么最后是普通四轮，不是麦轮

最初的白板上争的是"要速度还是要稳定"。定了四轮差速 + C8T6 + 四路灰度，然后在轮子上纠结了很久：麦轮能横移，理论上在中心资源区更灵活。

我们真的做了。`CAR1.0` 到 `car1.3` 五个版本全是麦轮解算：双轴摇杆两路 ADC、四路独立 PWM、前轮后轮分组。但从代码里能看出它是怎么死的——不是被改坏的，是被**换掉**的。

| | `car1.3`（12-02 23:20，麦轮最后一版） | `car2.0`（12-06 15:14，重启第一版） |
|---|---|---|
| ADC | 两路（PA0 / PA1，双轴摇杆） | **零** |
| PWM | TIM1 四通道 CH1–CH4 | TIM2 **两**通道 |
| 串口 | 无 | USART1（PA9 / PA10，蓝牙） |
| 方向电平 | 8 个 GPIO 输出 | 4 个 |
| main.c | 331 行 | **180 行，`while(1)` 里一行代码都没有** |

外设从"四个电机 + 摇杆"变成"两个电机 + 蓝牙"，这不是重构能解释的——是**物理底盘换了**。四个麦轮电机变成两个 TT 电机，摇杆换成手机蓝牙。

再看时间：`car1.3` 停在 12-02 23:20，`car2.0` 出生在 12-06 15:14，**中间空了三天半，一个版本都没有**。那三天半不在写代码，在换硬件和等件。

所以这段结论不需要回忆，代码自己写得比记忆清楚：**没时间把麦轮调出来，就换了一辆更简单的车。** 代码只能跟着车重建，`car2.0` 就是那时候新建的 CubeMX 空工程，只初始化了三个外设，主循环里空着。

后来 `car2.1`（12-11）把四轮独立控制和蓝牙控车补回来，同时第一次挂上四路灰度输入（PB12–PB15）。也就是说，**从 12-02 到 12-11 这九天，这辆车是看不见黑线的**，只能纯手操。

## 三、15 份代码是怎么长出来的

归档里 17 个目录，但把它们摊开看，口径得改一下：`CAR1.1_NOM` 和 `CAR1.2_NOM` 的 `main.c` md5 完全一致（那天只动了工程配置，没动代码）；`无麦仑成品BKUP` 和 `car2.1` 也完全一致（纯备份点）。所以是 **17 个目录、15 份不同的代码**。

## 四、循迹：把"修正量"调小是个陷阱

硬件是四路灰度，PB12–PB15 从左到右 L1 / L2 / R1 / R2，**低电平 = 压到黑线**。

判线就六个分支：

| 触发条件 | 行为 | car2.3 定稿 | 参赛版 |
|---|---|---|---|
| L2 + R1（双中间） | 直行 | 200 | 200 |
| 仅 L2 / 仅 R1 | 单侧微调 | **50** | **190** |
| L1 + L2 / R2 + R1 | 中幅转向 | **120** | **170** |
| 仅 L1 / 仅 R2 | 90° 硬转弯（原地差速 + 延时 300 ms） | 180 | 180 |
| 四路全无 | 停止 | 0 | 0 |
| — | 寻线重试 | — | 150，最多 2 次 |

{{< archify src="/archify/line-decide.html" wide="1" caption="主循环每 10 ms 跑一遍：先看是不是冲坡那 8 秒，再过全黑、全白两道门，最后才按四路组合判方向。" >}}

那两行被改大的数字，是这篇最值钱的一条经验。

一开始的想法很自然：偏一点点，就慢慢修回去，所以微调速度给了 50。实际跑起来是这样的——车压在线上偏了半厘米，你给一个 50 的速度让它蹭回来，**修正量不够，还没修回来车已经冲出线了**；一出一出，四路全白，进寻线逻辑，越跑越歪。

参数最后被整体往上抬：微调 50 → 190，中幅 120 → 170。逻辑变成了"轻轻地纠正是纠正不动的，要偏就偏得够狠、但只偏很短的时间"。这也顺便解释了为什么微调、中幅、硬弯三种转向配了三个不同的延时（50 / 150 / 300 ms）——**速度只是幅度，延时才是纠正的力度**，两个一起调才对。

### 冲坡这 8 秒

赛道有个坡。参赛版里有一句：

```c
#define LINE_SPEED_UPHILL   600   // 冲坡高速度
#define LINE_UPHILL_TIME    8000  // 冲坡时间（8 秒，单位 ms）
```

进循迹模式后的**前 8 秒，用 600 的速度冲，并且主动关掉全黑/全白检测**。原因很实在：上坡时车身姿态是翘的，四个探头会同时压在白区上，`IS_ALL_WHITE()` 立刻成立，车就在坡中间开始原地找线，然后滑下来。

所以这 8 秒里不检测，只看线跑；8 秒后恢复检测、降回平地速度 200。

这个"4 秒改 8 秒"是临时加上去的：归档里两份文件的时间戳相隔 4 分钟（12-20 15:44 与 15:48），前一份头部写着"新增巡线前 4 秒高速度冲坡"，后一份是"8 秒 + 关闭全黑/全白检测"。备赛记录里这一版记的是 12-19 18:51，跟文件时间戳对不上，我没有第二种证据去判定哪个准；能确认的只有一点——4 秒翻成 8 秒，且它发生在最后一天。

比赛是 12-20。冲坡能力不够，是把时间加长最直接的解法。

## 五、一个字节的蓝牙协议

遥控走 USART1 中断，一帧就是一个 ASCII 字符，加上 50 ms 防抖（同一个字符 50 ms 内重复直接丢弃）。

| 指令 | 含义 | 指令 | 含义 |
|---|---|---|---|
| `X` | 停止 | `M` | 模式切换（蓝牙 ↔ 循迹） |
| `W` / `S` | 前进 / 后退 | `Z` / `C` | 扫弹电机开 / 关 |
| `A` / `D` | 左转 / 右转 | `Y` | 扫弹电机组反转 |
| `Q` / `E` / `R` | 舵机 30° / 90° / 150° | `1` / `2` / `3` | 速度挡位 300 / 500 / 700 |

单字节的好处是中断里不用做协议解析，收到就进缓存，主循环里再执行。坏处也在这——**没有校验、没有重传**。比赛第一轮吃了这个亏：蓝牙频繁断连，指令丢了就是丢了，车按上一秒的指令一直跑。

## 六、比赛当天

上午到场地，第一个问题不是代码，是车身。视觉组队友试的时候发现，纯白的车身在摄像头里跟白底场地几乎分不开，识别框一直在飘。我们当场决定改颜色——我跑去校门口买黑色电工胶布，回来把车身贴满。

真正上场的时候，自动阶段一次都没跑成。有时候是按下蓝牙没反应，有时候是冲不上去坡。后两轮我们干脆放弃自动巡线，**全靠手动遥控把 45 秒跑完**。

三轮，每轮四台车。

**第一轮**：蓝牙一直断，指令丢一片，时间全耗在找回连接上。
**第二轮**：状态很猛。功率上去了，扫弹效率起来，得分很多。
**第二轮和第三轮之间**：测试时发现滚筒转速变慢，判断是电机烧了，紧急换备用电机。
**第三轮**：按下遥控，滚筒转得很别扭，一个球都扫不上去，只能遗憾离场。

赛后拆开看：**备用电机装反了。**

这就是比赛。不是算法崩了，不是现场没电，是一个方向反了的接线——装配的时候没人在那个环节停下来确认一下，代码也不会因为你装反就报警，它只会按你给的方向电平尽职地转。

### 那条没装的互锁

最终版的控制入口是这样：

```c
void Car_Control(Car_CmdTypeDef cmd) {
    switch(cmd) {
        ...
        case CMD_TT_MOTOR_ON:
            TT_Motor_Group_On();      // 收到就开，不看当前模式
            break;
        case CMD_TT_MOTOR_REVERSE:
            TT_Motor_Group_Reverse(); // 同上
            break;
    }
}
```

`Mode_Switch()` 只管"蓝牙 ↔ 循迹"的切换和停车，管不到扫弹。也就是说自动阶段那 45 秒里守不守规矩，**完全取决于操作手手里那台手机别按错**。

堵住它只要一行：

```c
case CMD_TT_MOTOR_ON:
    if (current_mode == MODE_LINE_WALKING) break;  // 自动阶段，拒绝
    TT_Motor_Group_On();
    break;
```

当时根本没意识到这是一个漏洞。是赛后复盘、把代码和规则一条条对着看的时候才发现的，写下来记在这。

## 八、还没修好的

- **互锁仍然没加。** 归档里那份 866 行的参赛固件就是原样，我没有回头补那两行——留着它当一个具体的物证，比改了更记得住。
- **电机装反没有任何防错。** 机械上没做不对称的接插件，电气上没有方向自检，代码里也没有上电自测。三轮比赛的最后一次机会，输在一个人人都能做对的环节上。
- **比赛结果没有凭证。** 八强只有群里的记录，没有官方名次文件，也没有奖状。
- **电路组那一堆增益凭证是零。** 规则里自研最小系统、PCB、驱动、降压模块每一项都能叠加加分，我们实际做了板子，但图纸和过程的凭证没留下。
- **视觉组只到车头小灯。** 装甲板识别写了代码，没到能联动扫弹的程度。

## 九、小结

866 行代码里，真正决定成绩的其实是几十个数字——微调 190、冲坡 600 跑 8 秒、硬弯 180 加 300 ms 延时。这些数字没有一个是推导出来的，全是在地板上、瓷砖上、白纸画的线上试出来的。

但最后输掉那一轮的不是这些数字。

是一台装反的电机，和一行没写的判断。

它们其实是同一件事：**你把"这次先这样"写进系统里，比赛当天就要拿运气去补。** 代码不会因为装反就报警，固件也不会因为你违规就自己停下——你不给它判断的能力，它就只有服从的能力。
